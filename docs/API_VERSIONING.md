# API 版本策略（029）

## 版本现状

| 版本 | 路径前缀 | 状态 | 说明 |
|---|---|---|---|
| v1 | `/api/v1/*` | **稳定版（当前）** | 组织、作品、认证等新体系接口；统一响应信封、业务错误码 |
| legacy | `/api/*`（无 v1 前缀） | 兼容保留 | ideas/storyboard/risk-check/export/feasibility/delivery-check 等老接口；保持原有请求/响应格式不变 |

注意：`backend/api/v1/` 目录下同时放着 legacy 路由文件
（`ideas.py`、`risks.py`、`exports.py`、`feasibility.py`，022 拆分时为收敛目录结构），
它们挂载时**没有** `/api/v1` 前缀，走的仍是老 `/api/*` 路径与原格式。
判断版本看 URL 前缀，不看文件目录。

## 响应格式

- **v1**：统一信封。成功 `{"code":0,"data":...,"request_id":"..."}`；
  失败 `{"code":非0,"message":"...","request_id":"...","details":...}`。
  删除类接口返回 `204 No Content`（无响应体，视为成功）。
  业务错误码见 `backend/core/error_codes.py`。
- **legacy**：保持原格式。成功返回裸业务 JSON；失败返回 `{"detail": "..."}`。

## 升级规则

1. **v1 为稳定版**：v1 内只做向后兼容的变更——新增可选字段、新增接口、
   新增错误码。已发布的字段不改名、不改类型、不删除。
2. **破坏性变更才升 v2**：如必须改（字段改名/类型变更/删除接口/鉴权方式变更），
   开 `/api/v2/*` 新前缀，v1 保持不动。
3. **老版本保留期**：v(n) 被 v(n+1) 取代后，继续提供服务 **6 个月**，
   期间响应头 `Sunset` 标注下线日期；到期后下线并在更新日志公告。
4. **legacy `/api/*`**：视为 v0，不再新增功能；新功能一律进 v1。
   未来如下线，需提前 6 个月公告并提供迁移指南。
5. **错误码只增不改**：已发布错误码的含义永久不变；废弃码保留在
   `error_codes.py` 中并标注 deprecated，不复用其数值。

## 给前端的约定

- 按 `code` 而非 HTTP 状态做业务分支（`code==0` 即成功）；
- `request_id`（与响应头 `X-Request-ID` 同值）用于报障时定位；
- 客户端可透传 `X-Request-ID` 请求头，便于链路关联；
- 遇到未知 `code` 按通用失败处理并上报，不要硬编码全部码表。
