# 恢复指标 SLO（100）

## 定义

| 指标 | 目标 | 含义 |
|---|---|---|
| RPO（恢复点目标） | ≤ 24 小时 | 灾难发生时，最多丢失 24 小时内的数据 |
| RTO（恢复时间目标） | ≤ 4 小时 | 从确认故障到服务恢复，最长 4 小时 |

## 如何达到 RPO ≤ 24h

- `scripts/backup.py` 每日凌晨 2 点自动备份（cron）；
- 备份保留 30 天，任意一天的备份都可用于恢复；
- 最坏情况：故障发生在下次备份前 1 分钟，丢失 < 24h 数据。

测量方法：

```bash
# 检查最近一次成功备份的时间
ls -lt backend/backups/ | head -2
# 计算距离现在的小时数，应 < 24
```

告警：备份脚本返回非零退出码 → 当天必须人工介入补备份，
否则 RPO 承诺即被打破。

## 如何达到 RTO ≤ 4h

故障恢复时间分解（预算）：

| 阶段 | 预算 |
|---|---|
| 发现与确认（监控告警/用户上报） | 30 分钟 |
| 决策（恢复到哪个备份点） | 15 分钟 |
| 恢复执行（`restore.py --target` + 行数校验） | 60 分钟 |
| 冒烟验证（登录/打开作品/新建保存） | 45 分钟 |
| 服务切换与观察 | 90 分钟 |
| **合计** | **4 小时** |

## 演练计划

- 每季度至少一次完整演练（见 docs/BACKUP_RESTORE.md）；
- 每次演练记录实际耗时，与上表对比，超时项必须有优化跟进；
- 演练覆盖两种场景：
  1. **数据损坏**：恢复最近备份到隔离库验证；
  2. **整库丢失**：从备份重建空库并启动应用。
