# 缓存策略设计（096）

> 状态：设计文档。Phase 4 引入 Redis 后实施；当前版本不引入缓存，
> 所有读请求直接走数据库，避免过早优化带来的一致性风险。

## 目标

- 高频读（作品列表、作品详情）P95 延迟 < 200ms；
- 缓存失效可预测：任何写操作后，读到的必须是新数据或明确过期的数据，
  不能出现"写了但读到旧数据且无人知道"的静默不一致。

## 缓存键规范

```
lupin:v1:{tenant}:{resource}:{id}:{dataver}
```

- `tenant`：org_id（租户隔离，键层面防串）。
- `resource`：`work` / `worklist` / `fact` 等。
- `dataver`：数据版本号，见下。
- TTL：作品详情 300s，作品列表 60s；写后主动失效，不依赖 TTL 兜底。

示例：`lupin:v1:org_abc:work:w_123:7`

## 版本关联方案（核心）

每个作品维护 `data_version` 整数（Phase 4 加列）：

1. 任何修改作品的写操作（PATCH / 分镜保存 / 恢复版本）在同一事务内 `data_version += 1`；
2. 读缓存时键中带 `dataver`；写后旧键自然失效，无需精确删除；
3. 列表缓存键带组织级 `org_version`，作品增删改时组织版本 +1。

这比"写后删键"更可靠：删键有竞态（删→并发写入→读到旧数据再缓存），
版本号方案下旧键的数据永远对应旧版本，不会污染。

## 失效时机矩阵

| 写操作 | 失效范围 |
|---|---|
| PATCH /works/{id} | 该作品详情键（版本+1）、所属组织列表键（org_version+1） |
| DELETE（软删除）/restore | 同上 |
| 版本恢复 | 同上（视为一次写） |
| 成员角色变更 | 该用户相关键（暂不缓存用户会话，Phase 4 定） |
| 事实库变更 | 作品键（事实内嵌于 data_json，作品版本+1） |

## 不缓存的内容

- 回收站列表（低频，实时性要求高）；
- 导出 JSON（体积大、低频）；
- 任何含权限判断的聚合视图（防止越权缓存）。
